05コア機能Core Features
01 — 一元管理
名簿も日程も、

サークル・イベント・掲示板・施設予約を、ひとつのアカウントで扱う。所属サークルの連絡は、そのメンバーにしか見えない。この可視範囲はアプリではなく、データベース側で決めている。

02 — カレンダー
参加登録した予定が、
そのまま載る

予定を見る場所は1つだけにした。同じ情報が一覧とダッシュボードに分かれていると、どちらを見ればいいのか分からなくなる。直近5件は横スライドのカードで、月表示のすぐ隣に置いた。

03 — 複数人の承認
判子が揃って、
はじめて通る

設立と廃止は、大学が決めた人数（1〜5人）が揃って成立する。却下はひとりで成立する。同じ職員が二度押すことはできない。誰がいつ何と書いて押したかは記録に残り、あとから辿れる。

04 — リマインド
何分前に知らせるかは、
本人が決める

参加登録したイベントごとに、通知のタイミングを個人単位で選ぶ。配信はデータベース側のスケジューラが5分おきに回す。日時が変わったイベントは、送信済みでも自動的に送り直しの対象へ戻る。

07書き込める場所を、ひとつに絞るSystem Architecture

作り込んだのは画面ではなく、権限の通り道だった。誰が何を書けるかの判断をコードの中に散らさず、データベースの一箇所に集めている。 この図で見てほしいのは矢印ではなく、通れないことを示す×印のほう。

1 学生が「参加する」を押すブラウザは指示を送るだけで、データベースの鍵は持たない
▸
2 Server Action が本人を確かめるlib/dal.ts を通る。ここを通らない読み書きの経路は存在しない
▸
3 RPC が権限を判定する学生か、対象は公開範囲の中か、すでに登録していないか
▸
4 書き込み、通知を1件つくる主催者に届く。同じ処理の中でやるので、片方だけ残ることがない
08権限モデルRow Level Security
Table読める人
universities / campuses全員（未ログインの大学一覧に必要）
student_profiles本人 ／ 同じサークルの仲間 ／ 所属大学の職員
circles学生・職員は承認済み全件、それ以外は公開設定のものだけ
circle_postsそのサークルのメンバーのみ
events可視範囲の判定に従う（未ログインは公開かつ掲載可のみ）
event_participants本人 ／ そのイベントの主催者
facility_reservations本人 ／ サークルのメンバー ／ 施設の大学の職員
approvals対象そのものが読める人
判定を、二箇所に分けない

RPC を SECURITY INVOKER のままにすると、RPC 内部の INSERT も呼び出し元の権限に従う。 すると「書き込みを許すポリシー」を別に書くことになり、判定が RPC の中の条件分岐とポリシーの二箇所に分かれてしまう。

全 RPC を SECURITY DEFINER にし、テーブルには書き込みポリシーを1つも置かない。 これで権限の判定が1箇所に閉じる。

09開発でこだわった点Development Focus
01
権限の昇格を、設計で塞ぐ

サインアップ時に渡すメタデータは、そのまま raw_user_meta_data に入る。つまり完全にクライアント側の制御下にある。ここを信用して役割を保存すると、curl 一発で職員権限のアカウントが作れてしまう。セルフ登録できる役割をトリガー側で絞り、職員の付与は別経路に分けた。

02
CDN に、認証済みの応答を載せない

Supabase の SSR ライブラリは 0.12 以降、Cookie を書き戻す関数の第2引数で no-store 系のヘッダーを渡してくる。これを応答に反映しないと、認証 Cookie 付きの応答が CDN にキャッシュされ、別の利用者にセッションが渡りうる。リリースノートを読んで初めて気づいた種類の変更だった。

03
サーバーとブラウザで、同じ乱数を出す

掲示板の紙は1枚ずつ傾きが違う。乱数を使うとサーバーでの描画とブラウザでの再水和で値がずれる。ID から決定的にハッシュを引くようにしたが、素朴な積和では連番の ID で値が固まり、傾きが目視でほぼ0になった。FNV-1a に murmur3 の最終撹拌を足して、分布の偏りを消している。

04
拡大率に依存しない背景

ブラウザの拡大縮小は rem も px も変えない。変わるのは、ビューポートに収まる CSS ピクセルの数のほうだ。固定配置の装飾を rem で組むと、引いて表示したときにだけ破綻する。単位を vw / vh / vmin に統一して解決した。
